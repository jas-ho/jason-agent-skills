# Transcript metrics and limits

The parser reads one explicitly selected JSONL file. It emits no message text, arguments, tool output, or token/cost/account data. It counts what is structurally present, not what a copied vendor comment claims each record contains. Representative source structures were inspected locally on 2026-09-12; tests use synthetic content with those shapes.

| Harness | Calls                                                                                          | Results                                                                                 | Identity                                   |
| ------- | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------ |
| CC      | assistant `message.content[]` blocks of `type: tool_use`, with `id`, `name`                    | user `message.content[]` blocks `type: tool_result`, `tool_use_id`, optional `is_error` | top-level `sessionId`                      |
| Codex   | `response_item.payload` of `type: function_call` or `custom_tool_call`, with `call_id`, `name` | corresponding `function_call_output` / `custom_tool_call_output`, with `call_id`        | `session_meta.payload.session_id` or `.id` |
| OMP     | `type: message`, `message.role: assistant`, content blocks `type: toolCall`, with `id`, `name` | `message.role: toolResult`, `toolCallId`, `toolName`, optional `isError`                | header `type: session`, `.id`              |

Call IDs deduplicate replayed/streamed blocks. Calls without an ID count separately as unidentified. A tool output with no visible input is an unmatched result, not an invented call. Repeated result IDs are counted once. Conflicting duplicate names/IDs appear in diagnostics. Invalid JSON, non-object lines and missing timestamps are reported. A file mixing recognizable harness formats is rejected rather than merged as one session; override is explicit.

`file_span_seconds` is max minus min recorded timestamp in the selected snapshot. It is elapsed file history, not active work or API time. Header/copied/forked history and OMP sibling branches can contribute; the parser does not reconstruct an active branch. Child transcripts are not traversed. Growing files can end with a partial malformed line; repeat on the same explicit identity only when a settled snapshot is needed.

`call_result_elapsed` measures a matched call record to its first result record. It includes scheduling, queueing and batching, so its top entries are elapsed spans, not measured execution bottlenecks. Missing/negative pairs are not assigned zero. In particular, nested calls inside Codex `functions.exec` may not have separate response_item records. Count them neither by regex-searching JavaScript nor by assuming one outer call equals one underlying operation.

Codex separately records some native `event_msg` / `item_completed` items. The parser reports `completed_tool_items` separately for CommandExecution, McpToolCall, DynamicToolCall, and CollabAgentToolCall when present, with exact item types. Rust `duration: {secs, nanos}` is an explicit duration; numeric duration with unknown units is not accepted. `started_at_ms`/`completed_at_ms` provides a separately labeled event elapsed duration when explicit duration is missing. Replayed item IDs deduplicate here too. These completion items are not added to top-level tool counts, because they can mirror those calls or represent nested execution. Other item types remain outside this tool timing inventory.

CC/OMP explicit `duration_ms`/`durationMs` on result blocks/messages is used only if present and numeric with nonnegative value. No schema-wide assumption that those fields exist is made. OMP task results can describe an entire worker duration; this is not evidence of durations for every nested tool. The parser does not add estimates into recorded totals.

Errors are separate evidence counts: explicit CC/OMP result error flags, structured Codex output error flags when the output is a JSON object, and failed/nonzero-exit native completion items. Missing error flags are unknown, not a clean bill of health. Free-form text containing “error” is not automatically a tool failure. Do not add the evidence categories together as independent failures; a single failure may appear in both a result and a completion item.

Subagent fields count structurally visible launch tool calls (`Agent`, `Task`, `task`, `spawn_agent`, including namespace-qualified variants), not successful child jobs. A launch can create multiple children or fail; parent logs do not establish child timing or success. Models, private payloads, and tool argument text are intentionally excluded from the metrics output.
